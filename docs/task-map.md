# Task Map

## 目的

Issue #1から分割したタスクと後続Issueの現在構造、状態、成果物、依存関係、次の議論位置を一覧できるようにする。

この文書は現在のスナップショットだけを示す。提案の変遷、分割理由、承認理由は[タスク分割議論記録](task-decomposition-discussion.md)に残す。

## ID規則

- `L<n>`: 大分類
- `L<n>-M<n>`: 中分類
- `L<n>-M<n>-S<n>`: 小分類
- 承認済みIDは原則として維持する。
- 議論中のタスクは承認時に名称・IDが変わる可能性がある。

## 状態

タスク構造の確定度と、実作業の進捗を分離して管理する。

### 計画状態

| 状態 | 意味 |
| --- | --- |
| 承認済み | タスクの存在、名称、親子関係が承認されている |
| 議論中 | 提案・監査済みだが、まだ承認されていない |
| 再検討中 | 承認済みだが、後続分割との矛盾に対する修正案があり再承認を待っている |
| 未分割 | 親タスクのみ承認済みで、子タスクをまだ議論していない |

### 実行状態

| 状態 | 意味 |
| --- | --- |
| 未着手 | 成果物の作成を開始していない |
| 進行中 | 成果物を作成中 |
| 完了 | 完了条件を満たした |
| ブロック | 依存関係や外部判断により進行できない |

### 分割完了度

分割完了度は計画状態と混在させない。2026-08-11時点でL1〜L8の全親タスクは小分類まで分割・独立監査済みであり、階層マップと台帳の全225 IDが承認済みである。

## 現在位置

- 現在の議論: なし（Task Map完成）
- 現在の状態: L1〜L8の全中分類・小分類と全体整合を確定済み
- 直前の完了: 全階層の独立最終監査と指摘補正

## 更新規則

1. 分割案を提示した時点で、子タスクを「議論中」として追加する。
2. 承認後に「承認済み」へ変更し、議論経緯は`task-decomposition-discussion.md`へ追記する。
3. 実装開始・完了は「実行状態」だけを更新し、過去の承認記録を書き換えない。
4. タスクを統合・移動・削除する場合は、先に議論記録へ理由を残してから本マップを更新する。
5. 小分類は最終実行単位とし、子タスクを作らない。作業手順やチェック項目は小分類の完了条件として管理する。
6. 承認はその時点の暫定的な構造確定とし、後続分割で矛盾、欠落、重複、粒度不一致、階層誤りが判明した場合は承認済みタスクも修正候補に戻す。
7. 承認済みタスクを変更する場合は、旧構造を議論記録へ残し、影響範囲と移行対応を示した修正案を再承認してからTask Mapへ反映する。
8. GitHubを実行Trackerとして使う場合は、中分類Issueのチェックリストへ小分類を束ねてもよい。ただし、小分類のTask ID、個別状態、完了条件、直接依存を維持し、中分類Issueは全小分類の完了と対応Gateの通過後に閉じる。Task Map上のTask統合とは扱わない。
